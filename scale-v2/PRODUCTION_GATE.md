# FABLE-5 Production Gate

The product may be called production-ready only after every check below captures a receipt.

## Database and isolation
- Clean migration passes
- Migration rerun passes
- `fable5_app` is NOSUPERUSER and NOBYPASSRLS
- Tenant A cannot select, insert, update, or delete Tenant B records
- Transaction-local tenant context is cleared when a connection returns to the pool
- Backup restoration reproduces evidence, canon, and audit history

## Evidence integrity
- Skipped evidence states are refused
- RECEIPTED requires a receipt
- VERIFIED requires an independent verification
- MEASURED requires a typed measurement
- LEARNED requires a supported learning
- CANONIZED requires explicit promotion approval
- Contradictory evidence opens an escalation before canon promotion

## Receipt integrity
- The authoritative receipt hash is generated by the server from canonical `fable.receipt.v1` bytes; caller digests are stored only as `source_digest`
- Every receipt has a tenant-local monotonic `chain_sequence` and `previous_hash`
- Every receipt hash carries an Ed25519 signature, key ID, and public-key fingerprint
- Production startup refuses to run without an out-of-repository receipt signing private key and explicit key ID
- The configured public key matches the private key before the service starts
- Legacy receipts are sealed without changing their historical facts before a new receipt extends the chain
- Direct INSERT of an unsigned/unchained receipt is refused by PostgreSQL
- UPDATE and DELETE of sealed receipts are refused; corrections/reversals create new receipts instead
- Evidence events, verification records, and measurement records are append-only
- `GET /api/receipts/:id/verify` recomputes the canonical hash, verifies the Ed25519 signature, and checks adjacent chain links
- `GET /api/receipts/verify-chain` verifies the complete tenant receipt chain and reports any gap, broken link, invalid signature, or unsealed legacy row
- An exported proof verifies offline with `npm run receipts:verify -- <proof.json>` using only the public key embedded in the proof
- Mutating a signed receipt field, the previous-hash link, or the signature causes verification to fail

## Engines
- Engine 00 refuses weak evidence even when market excitement is high
- Engine 01 cannot run before Engine 00 authorization
- Engine 02 requires willingness-to-pay evidence
- Engine 03 requires artifact verification
- Engine 04 requires measured distribution evidence
- Engine 05 revenue has a processor or ledger receipt
- Engine 06 requires REPLICATION-READY maturity
- Every engine reads and writes Engine 07
- Engine 08 returns `executed=false` without an enabled approved connector

## Operations
- Health endpoint fails closed when PostgreSQL is unavailable
- Startup does not print ready before database health succeeds
- Session tokens are hashed at rest and expire
- Outbox jobs are retryable without duplicate effects
- Structured logs contain correlation IDs
- Secrets are not committed
- Receipt signing private keys are held only in deployment secret/KMS custody, never in the repository
- Key rotation preserves old public-key fingerprints so previously exported proofs remain independently verifiable

## Compliance boundary
- These controls create technical evidence useful for SOC 2 readiness and audit support
- FABLE-5 does not claim SOC 2 Type I or Type II certification until an independent auditor has issued the applicable report
